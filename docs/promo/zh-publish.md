小明是一家公司的业务主管。季度经营分析会开到一半，他脑子里惦记着另一件事：早上八点丢给 **Hermes Agent** 的月度经营报表任务。

这类活儿很典型——从业务库里取数、按业务口径核对、再生成 Excel 和 PPT 两版。换成人做，是断断续续两天：等数、对不上再问、格式来回改。交给 Hermes Agent，一个上午能跑完。但它同时也是"会碰到东西"的任务：要写共享目录、要清理旧版本、中途还要执行几条脚本。

十点十分，手机在桌上震了一下。Hermes Agent 想清理上一季度的历史报表——

卡片上写着：`rm -rf reports/2026-09/`，理由是「避免新旧两版口径混淆」。破坏性操作，所以它在等一句确认。

会议室里没有电脑。走回工位至少十分钟，而审批窗口不会等人——要么现在在手机上点一下「本次批准」，要么看着任务超时、被默认拒绝、从头再来。

问题不在于"他没有一个能和 Hermes 聊天的地方"——企业微信能聊天，个人微信也能，企业微信甚至支持审批：它会把四选一的提示发进对话，回 `/approve` 就批了。

但一个业务主管不会去记这条命令。他要的是：弹出来的是什么、点哪里、还剩几秒。

于是有了 HermesPaw：一个鸿蒙（HarmonyOS NEXT）原生客户端，纯 ArkTS，零第三方运行时依赖，MIT 开源。

这类场景，就是我开始写它的原因。

## 先说清楚它不做什么

它**不做公网中继**，也**不经过任何第三方 IM**：手机必须和跑 Hermes 的那台机器在**同一个局域网**。离开这个网段，它就连不上。

这是刻意选的，不是没做完。审批是一个"人要在几十秒内当场决定"的动作，把它暴露在公网上，风险只会更大。

## 那为什么不直接用企微/微信？

这是我做完之后被问得最多的一句，也是最值得认真回答的一句。**企业微信通道是支持审批的**——我在网关源码里核对过：它会以文本形式下发一个四选一的提示（本次 / 本会话 / 固定 / 拒绝），你回 `/approve`（或者直接回 `yes`）就批了，回 `/deny` 就拒，网关的默认窗口是 300 秒，超时默认拒绝。

能用，也确实好用。但它有四个"容易出事"的地方：

1. **看不见全局状态**。聊天窗口里，一条审批提示很容易被后面的消息淹没，你甚至想不起来自己正卡在一个待决动作上。
2. **窗口太长**。300 秒里插进别的事太容易，五分钟之后你可能已经忘了自己在批什么，然后"顺手批了"。
3. **没有倒计时的紧迫感**。文本里写了截止时间，但它是静态的，不会随着剩余时间减少而催你。
4. **移动端打字成本**。在手机上敲 `/approve` 比点一下按钮慢；对不常敲命令的业务角色，这一步本身就劝退——而审批恰恰经常发生在他们身上。

所以两者的关系是**分工，不是替代**：

- 人在外面（出差、通勤），只需要收通知、发指令 → 用企微/微信通道，它有推送，跨网可用。
- 人在同一局域网、但不在电脑前（换个房间、开会、沙发） → 用 HermesPaw，它操作面深。

完整的十项对比（安装、网络、推送、审批、停止、插话、历史会话、长输出、多网关、内容外泄面）我写成了一篇文档，每一条都标了网关源码位置，欢迎来挑错：`docs/channel-comparison.md`。

## 三个别处没有的能力

### 一、审批卡片：四个选项，60 秒，默认拒绝

危险命令触发审批时，App 会弹出一张卡片：

```text
需要审批
chmod -R 777 /tmp/example
[本次批准] [本会话批准] [固定允许] [拒绝]
                    剩余 60 秒 · 超时自动拒绝
```

三条路径我都在真机上验过：

- **批准**：靶目录权限 `700 → 777`，命令退出码 0；
- **拒绝**：目录保持 `700`，模型明确回复"不做重试"；
- **不点**：60 秒到点自动拒绝，目录保持 `700`。

这条链路当时还踩过一个坑：网关返回的审批数据在 `pending_controls` 字段里，不是直觉上的顶层 `approval`。我第一版照着直觉写，卡片永远不弹——查源码才定位到。

### 二、`/steer` 插话：不用停掉重来

跑偏了不必"停止 + 重新提问"。直接在输入框里发一句话，就是插话：任务继续跑，但按新指令纠偏。

```text
已插入
插话未被接受
```

两个状态都有明确回显——没有回显的插话，等于没插。

### 三、run 状态与时间戳：知道它到底在干什么

顶部状态条只有三种状态：**有增量** / **无增量** / **兜底**。每条消息底下带时间戳：

```text
10:26:44 收 · 用时 639.3 秒
```

为什么这个 639.3 秒重要？因为长任务里"看起来卡住"和"真的卡住"完全是两件事。那天它跑了十分钟，状态条一直在动，我知道它没死——这比任何动画都让人安心。

（顺便说个真事：跑长回答时，`outLen` 桩了 393 秒都是 0，服务端最后给出 19611 个 output tokens。这不是 App 卡住，是模型自己在吐字。客户端按设计不设"实际耗时上限"，只看 run 状态。）

## 三步上手（手机与网关在同一局域网）

```bash
# 1. 网关侧出码（零依赖，脚本会先自检，不通不出码）
python3 tools/hermes-paw-qr --name home

# 2. 手机扫这个码：设置 → 扫码配置
# 3. 回到对话页，顶部显示「已连接：home」，发一条消息即可
```

## 技术底牌（只占 20%，但这是我最想讲的部分）

### 为什么最后放弃了「流式上屏」

做这个 App 的第二个星期，我花最多时间的地方是 SSE——目标是"模型吐一个字，屏幕蹦一个字"。

结论是做不到，而且证据很干净：

- SSE 连接**全程存活**，首字节 0.07 秒就到了，35 秒收 3039 字节，`seq` 连续；
- 但增量帧 **0 次**，`outLen` 全程 0；
- `getRun` 轮询的中途 `output` 也是空的，**终态才给全**。

也就是说：网关（REST 面）并不推送逐字增量。既然拿不到增量，SSE 就只剩"证明连接还活着"这一个作用。

于是我把传输**主从反转**：`getRun` 轮询做基线（一次差分测量：10 次调用 0 失败，P50 约 15 ms、最慢 39.6 ms），SSE 降级为增强。最坏路径从"SSE 失败 + idle 30 秒"压到"一次 getRun"。轮询起步 2 秒，慢下来封顶 5 秒，终态立即收口，退到后台停轮询。

这不是"没做出流式"，是**知道了边界在哪，把力气挪到能改善的地方**（等待态 UI + 时间戳）。

### 会话标题为什么不自己起名

第一版我给新会话起了个占位名「新对话 70384」，结果服务端的自动命名永远不生效——因为占位名把 `set_auto_title` 封死了。

改法是：**不传 title**，让服务端先 `derive_title`（取首条消息首个有意义行，≤48 字符），再由 aux 模型升级成 3–7 个词。现在新会话的 `title_source` 是 `llm`，标题是「Confirm end-to-end testing ok」这种人能看懂的名字，而不是一串时间戳。

### 206 处硬编码中文：非 Web 前端的 i18n 长什么样

鸿蒙的 `$r('app.string.x')` 只能在声明式 UI 里用，ViewModel 和网络层用不了。于是所有错误提示、状态文案、气泡后缀，全是我一开始直接写死的中文——**206 处**。

收口办法：新增一个 `Msg` 门面（启动时注入 `resourceManager`，之后统一 `Msg.t('key')`），文案全部进 `base / zh_CN / en_US` 三套 `string.json`（各 345 个 key），再补一道门禁：三语 key 集合必须一致、`en_US` 不许残留中文、代码区不许出现中文字面量、`Msg.t` 引用的 key 必须存在。

踩的坑也值得记一笔：

- 资源名**不允许点号**（只允许 `[a-zA-Z0-9_]`），第一次打包直接失败；
- 去点号后与既有的 163 个 key 撞名，最后统一加 `m_` 前缀；
- 用正则批量替换会把**注释里的引号**当成配对起点，把一行注释改成 `Msg.t('...')` 的碎片——只能写四态词法器（代码 / 单双引号 / 行注释 / 块注释）重做。

## 最后

这个 App 很小：41 个 ArkTS 源文件（外加 4 个设备测试文件）、零第三方运行时依赖、单 HAP。它也不完美：只有局域网能用、没有推送、流式上屏做不到。

但它解决了一个很具体的问题——**我不在电脑前的时候，还是能对这个 agent 负责**。

如果你也在跑 Hermes，欢迎试试；如果你只用企微/微信通道，那也完全合理，那是另一条很成熟的路径。
