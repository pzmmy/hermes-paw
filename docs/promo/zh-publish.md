小明是一家公司的业务主管。季度经营分析会开到一半，他还在惦记早上八点丢给 Hermes Agent 的那份月度经营报表。

这个活交给 Agent 很合适。从业务库取数，按业务口径核对，出 Excel 和 PPT 两版。以前是人做，断断续续两天：等数、对不上再回去问、格式改三遍。现在一个上午就完了。

问题是它也会碰到东西。写共享目录、清理旧版本、跑几条脚本。这些动作不带眼睛，我不敢让它随便做。

十点十分，手机在桌上震了一下。Agent 想清理上一季度的历史报表，等他确认。

卡片上写着命令 `rm -rf reports/2026-09/`，还有一行理由是「避免新旧两版口径混淆」。说实话这行理由比命令本身要紧，因为他看不懂 `rm -rf`。

会议室里没有电脑。走回工位十分钟，回来这条已经超时，默认拒绝，任务从头再来。

所以我写了个客户端。

## 先说它不能干什么

只能同一个局域网。手机和跑 Hermes 的那台机器在同一个网段，能连；出了这个网段就是个砖头。

这是我自己定的，不是没做完。审批这种事，人得在几十秒内当场拍板。把这条链路挂到公网上，我睡不着。

## 那企微不行吗

行。我一开始也是这么想的。

企业微信通道支持审批，我翻了网关源码确认过。它把四选一的提示发到对话里，回 `/approve` 就批，回 `/deny` 就拒，还认 `yes`。默认窗口 300 秒，超时默认拒绝。

能用。但我自己用下来有几处别扭。

一条审批提示发进聊天，很容易被后面几条消息顶走。等你想起来，可能已经顺手批了另一件事。300 秒听着不短，可你正在开会，五分钟里能插进多少别的事。文本里写了截止时间，但那个时间是死的，不会随着秒数变少来催你。

还有一点对我上面那个小明很要命：他得记住 `/approve`。业务角色不会记这个。

所以这两个是分工，不是谁替代谁。人在外面出差，只需要收通知、发句话，企微更合适，它有推送，跨网也能用。人在办公室但不在座位上，用客户端。

十几项对比我写成文档了，每条都标了网关源码位置，欢迎来挑错：`docs/channel-comparison.md`。

## 审批卡

危险命令触发审批时会弹卡片。四个选项：本次、本会话、固定、拒绝。底下 60 秒倒计时，到点自动拒绝。

三条路径都在真机上点过。批准之后靶目录权限从 `700` 变成 `777`，命令退出码 0。拒绝之后目录还是 `700`，模型明确说不重试。放在那儿不管，60 秒后自动拒绝，目录依然 `700`。

这里踩过一个坑。

网关返回的审批数据在 `pending_controls` 字段里，不在顶层 `approval`。我第一版按直觉写，卡片永远不弹。日志里没有任何错误，就是没反应。翻了半天源码才看出来字段名不对，改完一次就出来了。

从那以后我对"没报错但也没效果"这种状态特别警惕。

## 插话

Agent 跑偏了，不用停掉重来。

在输入框发一句话就是插话，任务继续跑，但按新指令走。App 会回两句话之一：`已插入`，或者 `插话未被接受`。

两个都得有。没有回显的插话，你根本不知道那句话进去没有。

## 状态条和时间戳

顶上只有三种状态：有增量、无增量、兜底。每条消息底下带时间戳，像这样：`10:26:44 收 · 用时 639.3 秒`。

为什么在乎这个 639.3 秒。因为"看着卡住"和"真的卡住"是两回事。

那天这个任务跑了十分钟。中途我盯着日志，`outLen` 一共 393 秒都是 0。要是按"多少秒没动静就判死"的逻辑，它早被我自己杀了。但状态一直是 running，服务端最后吐了 19611 个 output tokens。

它没死，只是在写。

所以客户端里没有"实际耗时上限"这种东西，只看 run 的状态。

## 三步装起来

手机和网关在同一个局域网，然后：

```bash
python3 tools/hermes-paw-qr --name home
```

这条命令会先自己探一下 `/v1/models`，探不通就不出码。所以码能出来，基本就代表手机马上能连。

扫码，进设置页扫，回对话页，顶上显示「已连接：home」。

出码串里带长效 key。一人一码，别截图，别发群。

## 技术部分

### 流式上屏，我放弃了

做这个 App 第二周，大部分时间都在弄 SSE。目标很朴素：模型吐一个字，屏幕蹦一个字。

没做成。而且证据很干净。

SSE 连接是活的。首字节 0.07 秒就到了，35 秒收了 3039 字节，`seq` 连续不断。可是增量帧 0 次，`outLen` 一路 0。

我又去试轮询的中途快照，`output` 也是空的，只有终态才给全。

也就是说网关这条 REST 路根本不推逐字增量。拿不到增量，SSE 剩下来的作用就是证明连接还活着。

那我就把主从关系倒过来。轮询当基线，SSE 降级做增强。一次差分测量的结果是 10 次调用 0 失败、P50 约 15 ms、最慢 39.6 ms。这个数是一次性手工量的，脚本没固化成工具，所以对外我只写"约 15 ms"。

轮询从 2 秒起步，慢下来封顶 5 秒，终态立刻收，退到后台就停。

不是我硬要做流式没做出来，是这条路走不通，我把力气挪到等待态的界面和时间戳上了。那两样至少让人知道它还在动。

### 标题别自己起名

第一版我给新会话起了个占位名，叫「新对话 70384」。

结果服务端的自动命名永远不生效。因为占位名把 `set_auto_title` 锁死了。

后来改成不传 title。服务端先按首条消息取一行，48 字以内，再让 aux 模型升级成三到七个词。现在新会话的 `title_source` 是 `llm`，标题是「Confirm end-to-end testing ok」这种人话，不是一串时间戳。

### 206 处硬编码中文

鸿蒙的 `$r('app.string.x')` 只能在声明式 UI 里用，ViewModel 和网络层用不了。所以错误提示、状态文案、气泡后缀，我一开始全写死成中文了。数了一下，206 处。

补法不复杂。加一个 `Msg` 门面，启动时注入 `resourceManager`，之后统一 `Msg.t('key')`。文案全进 `base / zh_CN / en_US` 三套 `string.json`，每套 345 个 key。再补一道门禁查四件事：三语 key 必须一样多、`en_US` 不许留中文、代码区不许出现中文字面量、`Msg.t` 的 key 必须真存在。

坑都在细节里。

资源名不允许点号，只允许字母数字下划线。第一次打包直接失败，报错就一句话。

把点去掉之后，新的 key 跟原有的 163 个撞了名。最后统一加 `m_` 前缀。

最惨的是批量替换。我用正则改，结果正则把注释里的引号也当成配对起点，把一行注释改成了 `Msg.t('...')` 的碎片。改坏了十几处才发现，只能整体回滚，写了个四态词法器重做。代码、单双引号、行注释、块注释分开处理，才干净。

## 最后

这个 App 不大。41 个 ArkTS 源文件，加 4 个设备测试文件，零第三方运行时依赖，一个 HAP。

它也不好。只能局域网用，没有推送，流式上屏做不到。

但它解决了我一个很具体的麻烦：人不在电脑前的时候，我还想对这个 Agent 负责。

如果你也在跑 Hermes，可以试试。如果你就用企微或微信通道，那也挺合理，那是另一条走了很久的路。
